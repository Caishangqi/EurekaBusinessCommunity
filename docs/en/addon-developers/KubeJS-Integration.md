# Retail KubeJS integration

EurekaBusiness Retail KubeJS is an optional Retail adapter. It provides a bounded declarative script API for customer variants, decorations, catalog entries, tips, and selected customer policies. Scripts cannot directly control transactions, inventories, pathfinding, or customer behavior.

## Installation

Install the following on the dedicated server and on clients that connect to an adapter-enabled server:

- EurekaBusiness Core and Retail.
- The `eureka-business-retail-kubejs-neoforge` adapter.
- A KubeJS version compatible with the adapter.

When `startupContent` references blocks, models, or other content, clients must also produce the same structural declarations and provide resources explicitly declared with `resource()`. Server overlays used only by `serverContent` are outside this connection check.

The adapter registers two KubeJS events:

- `EurekaBusinessEvents.startupContent` for structural content.
- `EurekaBusinessEvents.serverContent` for reloadable server overlays.

## Content order and reloads

Retail combines content in this order:

1. Built in defaults.
2. Server Fzzy Config.
3. KubeJS server script overlay.

Place `startupContent` in `kubejs/startup_scripts`. It can declare elements, Retail customer variants, and decoration definitions. The connection check compares the structural declaration fingerprint generated by the server and client, plus resources explicitly declared with `resource()`. Script files do not need to match line for line when they produce the same declarations and resources. Restart after changing structural content.

Place `serverContent` in `kubejs/server_scripts`. It is recalculated during a server resource reload and can be updated with `/reload`. Each reload starts from the current Fzzy Config content, so removing a script declaration removes that overlay change.

Invalid candidate content does not apply partially. Retail retains the last accepted snapshot and writes a diagnostic to the server log. Existing customers, evaluated prices, reservations, settlements, and tip obligations keep the facts captured when they were created. Reloads affect later customers and new server decisions.

## Structural declarations

This example uses a normal KubeJS block registration, then declares that block and a vanilla block as decorations:

```js
StartupEvents.registry('minecraft:block', event => {
  event.create('shop_charm').displayName('Shop Charm')
})

EurekaBusinessEvents.startupContent(event => {
  event.decoration('kubejs:shop_charm', 'kubejs:shop_charm')
    .flat(15)

  event.decoration('kubejs:stone_display', 'minecraft:stone')
    .element('eurekabusinesscore:element_terra', 5)
})
```

`event.decoration(id, blockId)` accepts any registered vanilla, mod, or normal KubeJS block whose default state is not air. One block ID can have one decoration definition. A declared decoration blocks Retail customer pathfinding inside the shop. Customers cannot cross it, stand on it, or use it as a step. The rule applies only to Retail customers. It does not change the block's world collision, interaction, or pathfinding behavior for other entities.

Do not declare a floor, stair, or corridor block that customers need to use. A registered block without a block item can be declared, but players cannot place it through a normal item.

The old `eurekabusinessretailkubejs:shop_decoration` builder has been removed. Existing blocks created by that builder are not converted automatically. Back up the world, replace those blocks in the old version, and update the scripts before upgrading.

## Server overlays

`serverContent` is a declarative editor. It collects validated data and does not expose live registries, entities, inventories, or server objects to scripts.

```js
EurekaBusinessEvents.serverContent(event => {
  event.catalogPut('minecraft:amethyst_shard',
    5, 15,
    16, 45,
    46, 90,
    91, 150)
  event.catalogAddElement('minecraft:amethyst_shard',
    'eurekabusinesscore:element_vitreus', 2)

  event.enableVariant('eurekabusinessretail:customer.mage')
  event.variantPolicy('eurekabusinessretail:customer.mage')
    .spawnCycle(300, 600)
    .spawnBatch(1, 2)
    .fixedRarity(25)

  event.decorationFlat('kubejs:shop_charm', 20)
})
```

Catalog operations include:

- `catalogHas`, `catalogGet`, and `catalogList`.
- `catalogPut` and `catalogRemove`.
- `catalogSetElement`, `catalogClearElements`, `catalogAddElement`, and `catalogRemoveElement`.

Customer operations include:

- `enableVariant`, `disableVariant`, and `variant`.
- `variantPolicy` for spawn cycle, spawn batch, purchase profile, browse budget, navigation budget, wander profile, rarity, and continuation rules.
- `tips(variantId)` for fixed values, percentages, element percentages, and item reward rules.

Decoration operations include `decorationFlat`, `decorationElement`, `enableDecoration`, and `disableDecoration`. Server configuration cannot redirect a registered decoration to another block or disable the built in fallback customer variant. Catalog items, elements, variants, decorations, and tip rewards must use complete registered IDs.

## Script boundary

The adapter does not expose arbitrary business script execution. Do not run arbitrary JavaScript in transactions, server ticks, pathfinding, or customer behavior. Use the declarative events above for supported content changes. Retail keeps the rest of the game logic on the server.
